## 8.1 共享策略与机器操作

调度策略、任务解析、模块注册和 LaFS 格式处理属于共享逻辑；中断寄存器、页表编码与特权返回指令属于架构实现。

`kernel/arch_dispatch.h` 选择架构头文件，有助于集中展示接口，但不表示其余代码没有架构条件编译或历史命名。

`pml4_phys` 等名称仍存在于共享接口。实现其他页表格式时，应遵守物理页表根的含义，而非将历史名称解释为必须使用 x86_64 硬件。

## 8.2 接口还包含顺序与生命周期

| 接口 | x86_64 示例 | 移植须保持的性质 |
| --- | --- | --- |
| IRQ 状态 | 保存与恢复 RFLAGS 中断状态 | 恢复调用者原状态 |
| 上下文切换 | 内核栈与 FPU 保存区 | 挂起执行状态与寄存器归属 |
| 用户转换 | 首次 `iretq`、syscall `sysret` | 正确特权级、栈与返回状态 |
| 页表更新 | PTE 写入与 TLB 失效 | 复用或恢复访问前的可见性 |
| 远程唤醒 | 队列发布与重调度 IPI | 目标观察到已发布任务 |
| DMA 交接 | 描述符与缓冲区同步 | CPU 与设备对所有权及内容的理解一致 |

相同函数签名不能保证满足接口约束，遗漏屏障或错误恢复中断仍可能破坏语义。因此，架构功能对齐需要运行验证，不能只检查编译。

## 8.3 分阶段建立可观察的移植结果

先建立可靠早期输出与启动元数据，再实现物理分配和映射、本地异常与定时器、单线程调度及用户进入和返回。明确本地执行状态和栈模型后再增加 SMP。设备传输测试随后独立验证 DMA 和路由，不与文件系统或报文格式测试混为一谈。

各阶段应有具体观察结果，例如系统调用返回、另一 CPU 的确认或真实传输读取数据。启动标语不能代替这些结果。

## 8.4 按分支内容开展验证

当前检出提供 x86_64 实现。ARM64 实现及直接启动、UEFI/Limine 目标位于 `arm64` 分支，两类启动覆盖不同。实验性 RISC-V 目录不代表功能已经对齐。

共享代码工作流程从 `x86_64` 开始，验证后对 ARM64 变基并运行相关目标。修改共享代码前应查阅分支策略。历史移植审查仅记录当时状态，不是当前能力边界。

## 练习：审查一个架构接口

选择页表根切换或 IRQ 状态保存与恢复，阅读 x86_64 头文件及相关调用者，记录地址类型、本地中断状态、顺序要求和允许的执行上下文。

按 [覆盖矩阵](../design/testing/testing-arch.md#coverage-matrix)为每个性质选择测试，明确标记缺少测试的性质。构建目标存在不表示它对所有性质均有断言。

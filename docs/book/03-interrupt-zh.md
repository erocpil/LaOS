## 3.1 保存被中断的执行状态

中断可在未主动调用处理程序的代码中发生，因此普通 C 调用约定不足以保护被中断代码所需的状态。

`kernel/arch/x86_64/idt_stubs.S` 将硬件保存状态、规范化错误码、向量号和通用寄存器组织为 `struct interrupt_frame`，并向 C 处理程序传递其指针。

有硬件错误码与无硬件错误码的异常必须提供一致布局，否则缺失槽位之后的所有字段都会错位。

## 3.2 确定保存帧所在的栈

来自 ring 3 的中断使用 TSS 建立的内核栈状态。内核执行期间发生的普通中断保留在当前线程栈上。部分致命异常使用 IST 栈，以提高诊断路径在栈损坏时的可用性。

当前 x86_64 普通中断入口不切换到已分配的每 CPU IRQ 栈。分配了栈并不表示入口已经使用它。

## 3.3 调度可以挂起中断续执行上下文

考虑定时器在 write 系统调用期间触发：

```text
用户 write
  syscall 帧
    syscall C 调用帧
      中断帧 -> 定时器处理 -> 调度切换
                             其他线程运行
                         <- 原线程恢复
      iretq -> 恢复 syscall C 执行
  sysret -> 恢复用户执行
```

两类保存帧均留在原线程内核栈上。若另一挂起上下文复用同一存储区域，原线程就无法安全恢复。调度器的切换帧构成额外一层，不替代 syscall 帧或中断帧。

## 3.4 分发决定恢复方式

缺失用户映射可通过 VMA 路径修复；非法用户访问可能终止线程；内核异常进入诊断路径。结果由故障分类和当前上下文决定，不由 IDT 门是否存在单独决定。

外部设备 IRQ 则需处理或记录设备原因，并确认中断控制器。CPU 异常不需要 APIC EOI。具体异常显示见 [诊断教程](../design/diagnostics/diagnostics-tutor.md)。

## 3.5 IPI 传递跨 CPU 请求

内核通过 IPI 请求 TLB 失效、执行投递自测试及远程重调度。运行队列更新和 `need_resched` 发布必须先于通知，接收方随后处理已发布状态。

对于 TLB 操作，中断投递与所需失效操作完成是不同观察结果。这一区别直接影响页面回收正确性。

## 实验：分析返回路径

```sh
make test-x86_64-smp-tlb
```

检查 IPI 与重新映射验证，再沿汇编中的定时器返回路径定位调度点及寄存器恢复位置。与 syscall 返回比较，说明为何不能将一种保存帧传给另一种恢复代码。

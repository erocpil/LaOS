# e1000 架构

英文原文：[e1000 architecture](e1000-arch.md)。

## 适用范围

x86_64 e1000 驱动通过 `e1000.mo` 加载；ARM64 也在 direct 和 Limine 启动路径中包含内建 e1000 路径。两条路径均用于展示 PCI MMIO、DMA 描述符环、报文处理和中断通知。报文辅助接口尚未提供套接字、TCP 连接或通用 TCP/IP 协议栈，驱动也不是通用的多网卡绑定框架。

| 文件 | 职责 |
| --- | --- |
| `module/e1000.c` | 初始化、RX/TX 路径、工作线程模式与诊断 |
| `module/e1000.h` | 寄存器、描述符、环和报文类型 |
| `module/protocol.c`、`module/protocol.h` | 教学用报文辅助接口 |
| `kernel/pci.c` | 设备发现与配置空间访问 |
| `kernel/arch/x86_64/idt.c`、`kernel/arch/aarch64/idt.c` | 分发 e1000 IRQ 回调 |
| `conf/task.conf` | 默认模块部署与参数配置 |

## 初始化

`e1000_init()` 查找设备，获取并映射 BAR0，启用 PCI 地址译码和总线主控，复位控制器，读取 MAC 地址并准备 RX/TX 描述符环。提供给设备的描述符地址是物理地址；CPU 通过已映射的虚拟地址访问其存储区域。

x86_64 模块在驱动状态建立后向 IDT 层注册 `e1000_irq_handler()`，清除残留中断原因，并通过 INTx 路径启用接收相关中断。发现 MSI 能力不会自动启用该路径上的 MSI。
ARM64 路径会优先尝试 MSI；没有可用的 MSI 路由时回退到 INTx。

初始化具有完整性边界：

```text
匹配 PCI -> 映射 BAR0 -> 启用总线主控 -> 复位/读取 MAC
         -> RX 环和缓冲区 -> TX 环和缓冲区
         -> 注册 IRQ 回调 -> 启用中断原因
```

分配、映射或设备发现失败时，初始化必须在向设备暴露部分准备的描述符环之前停止。当前退出辅助函数会禁用 RX 并注销回调，但不构成完整的热拔出或模块卸载协议；回收代码或缓冲区前仍须协调工作线程、DMA 活动和所有未完成缓冲区。

寄存器契约有意保持较小。BAR0 通过驱动的 MMIO 辅助函数访问；`RCTL`/`TCTL` 启用收发引擎，`RDH`/`RDT` 和 `TDH`/`TDT` 划分描述符所有权，`ICR` 报告并清除中断原因，`IMS` 控制通知原因。写入尾指针寄存器是所有权发布，而不仅是更新进度计数。

## 描述符所有权

RX 和 TX 各使用 256 个描述符。RX 描述符指向已提供的接收缓冲区；TX 为各槽位配置缓冲区，并使用 `tx_lock` 串行化提交。驱动与设备通过描述符状态及环的头尾位置交接所有权。

```text
RX：可用缓冲区 -> 设备写入报文 -> 驱动观察到 DD
    -> 驱动消费报文 -> 向设备归还缓冲区和描述符

TX：驱动填充缓冲区和描述符 -> 推进尾指针 -> 设备发送
    -> 驱动观察到 DD -> 槽位可再次使用
```

TX 路径限制报文长度，并以超时方式等待完成。超时不能视为发送成功。同样，只要描述符或软件队列仍允许访问某个 RX 缓冲区，该缓冲区就不能释放或复用。

所有权转换是安全边界：

```text
RX：设备拥有描述符
      -- 观察到 DD --> CPU 拥有报文/缓冲区
      -- 释放或替换 --> 设备重新拥有描述符

TX：CPU 拥有空闲槽位
      -- 发布描述符和尾指针 --> 设备拥有槽位
      -- 观察到 DD --> CPU 拥有可复用槽位
```

CPU 必须先读取 RX 描述符的完成状态，再消费长度和报文数据。在软件消费者完成之前，不得写入 RX 尾指针或复用旧缓冲区。TX 在 `tx_lock` 保护下保持描述符及其后备缓冲区的预留状态，直到完成或超时处理结束。

## 接收模式

`g_rx_mode` 选择五种接收循环之一：简单轮询、批量接收、缓冲区替换式批量接收、单线程流水线或多线程流水线，默认值为 5。`g_idle_mode` 决定轮询尝试之间采用主动让出 CPU 还是休眠。

批量释放将已消费的描述符归还给环。缓冲区替换则向设备提供新缓冲区，并将已接收报文的原缓冲区交给软件处理。多线程路径增加软件队列和补充缓冲池，其所有权关系同时涉及硬件环和软件消费者。

切换接收模式会改变这些所有权转换过程，并非只调整每轮处理的报文数量上限。

不同模式的生命周期如下：

| 模式 | 观察 DD 后的软件所有权 | 由谁归还描述符 |
| --- | --- | --- |
| 简单轮询 | 调用者/报文处理器临时拥有缓冲区 | 报文处理后的轮询循环 |
| 批量接收 | 批量数组保留报文引用 | `e1000_rx_batch_release()` |
| 缓冲区替换 | 批量数组拥有已完成缓冲区，环立即获得替换缓冲区 | 替换路径立即归还，报文稍后释放 |
| 单线程流水线 | 软件队列拥有已完成缓冲区 | 队列消费者 |
| 多线程流水线 | 队列和空闲池共同划分报文/缓冲区所有权 | 消费者及 `e1000_rx_release_buffer()` |

因此，缓冲区替换和流水线模式不能使用简单轮询中“处理完报文再归还描述符”的假设。

## IRQ 与工作线程的职责边界

IRQ 回调读取 ICR、记录中断原因、发布接收待处理标志，并可将已注册的阻塞工作线程置为 READY。该回调不清空 RX 环；描述符消费仍由接收循环负责。

`e1000_wait_rx_event()` 提供待处理事件等待接口。该接口的存在不表示所有接收模式均采用中断驱动等待，应检查所选循环的实际调用位置。

回调面向单个全局驱动实例。当前中断路由、工作线程亲和性与通知机制尚未构成通用的多网卡事件子系统。

通知时序如下：

```text
设备触发 IRQ -> 处理程序读取 ICR 并记录原因
             -> 以 release 语义发布 rx_pending
             -> 可选地将阻塞工作线程置为 READY
             -> 工作线程/轮询循环消费描述符
             -> 工作线程清除待处理状态，再次等待
```

处理程序有意保持有界，不解析报文。IRQ 计数只能证明中断原因已投递，不能证明描述符已完成、补充、入队、消费或释放。

## DMA 顺序与生命周期

驱动在描述符及缓冲区所有权转换前后使用 `arch_dma_sync_for_cpu()` 和 `arch_dma_sync_for_device()`。硬件可见的描述符字段使用 volatile 修饰，但 volatile 本身不提供缓存维护或跨 CPU 的发布顺序保证。

QEMU/x86_64 上的一致性 DMA 行为不能验证其他架构的缓存维护。模块退出辅助接口也不等同于安全的通用卸载机制：回收代码或缓冲区之前，必须协调停止硬件访问、回调执行和工作线程引用。

## 架构边界

| 项目 | x86_64 | ARM64 |
| --- | --- | --- |
| 集成方式 | 可加载的 `e1000.mo` 模块 | Limine/direct 内核启动路径中的内建路径 |
| 中断分发 | 使用缓存 PCI IRQ 线的可加载模块 IDT 回调 | 内建回调路径，优先 MSI，INTx 作为回退 |
| 普通冒烟覆盖 | `-net none`，不证明数据面 | 网络化 direct/LaFS 实验，普通 Limine 冒烟不提供同等证明 |
| DMA 顺序证据 | 一致性 QEMU 行为及源码审查 | 源码审查和平台 DMA 钩子；数据面仍需运行流量验证 |

共享驱动代码不代表两个架构路径具有相同的启动、中断或网络覆盖。验证时应针对选定的启动路径，分别记录设备发现、中断投递、描述符进展和报文处理。

## 验证依据

标准 x86_64 冒烟测试禁用网络。设备与 IRQ 验证需要附加网卡，并按 [e1000 教程](e1000-tutor-zh.md)执行。应分别记录设备发现、初始化、中断原因投递和报文处理进展。IRQ 计数增加不能证明 RX 所有权交接或协议处理正确。

最小验证证据集如下：

| 证据 | 检查内容 |
| --- | --- |
| PCI/BAR 日志 | 设备匹配、BAR 映射和总线主控 |
| 初始化日志 | 复位、MAC 读取、描述符环分配和中断原因启用 |
| `[e1000] IRQ` 日志 | 中断原因投递及有界处理程序进展 |
| RX/TX 计数 | 描述符完成和软件路径进展 |
| 报文或 ping 轨迹 | 端到端缓冲区所有权和协议辅助路径进展 |

单一证据不能证明完整数据路径。

# 启动架构

英文原文：[Boot architecture](boot-arch.md)。

## 适用范围

本文说明当前目录中的 x86_64 Limine 启动路径。ARM64 实现位于 `arm64` 分支，直接启动和 Limine 路径需要分别评估。源码阅读步骤见 [启动教程](boot-tutor-zh.md)，整体过程见 [第 1 章](../../book/01-boot-zh.md)。

## 源码分工

| 文件 | 职责 |
| --- | --- |
| `kernel/arch/x86_64/main.c` | Limine 请求、BSP/AP 入口及启动任务准备 |
| `kernel/boot_limine.c` | 将 Limine 响应转换为共享启动记录 |
| `kernel/boot_info.h` | 内存映射与模块交接格式 |
| `kernel/hhdm.h` | 直接映射地址转换 |
| `kernel/arch/x86_64/cpu.c` | 每 CPU 状态与上线协调 |
| `kernel/task.c` | 构造并释放已配置任务 |

入口为 x86_64 链接脚本指定的 `kmain()`。启动信息来自 `.limine_requests` 中静态请求的响应字段，没有单个启动信息参数传入 `kmain()`。

## 启动信息所有权

`check_bootloader()` 检查基础修订版本以及所需 framebuffer、HHDM 和内存映射响应。在调用 `boot_info_from_limine()` 前先初始化直接映射偏移。

适配层将内存映射条目和模块描述符复制到静态数组，当前上限分别为 128 和 64。模块内容、路径和命令字符串仍通过指针引用，不是引导程序内存的深复制。回收引导程序存储之前，须明确审查这些指针的生命周期。

CPU 数限制为 `MAX_CPUS`。逻辑 CPU 编号来自 Limine CPU 数组，不应与可能不连续的 LAPIC ID 混淆。

启动记录具有借用存储边界。复制后的数组条目由 LaOS 管理，而模块内容、路径和命令字符串仍由指针引用并由引导程序管理。未来若要回收启动内存，必须先完成深复制，或证明所有消费者均已停止使用这些引用。

## BSP 初始化顺序

以下分组保持 `kmain()` 中的实际顺序：

1. 关闭本地 IRQ、建立早期 GS，初始化日志，检查启动响应，初始化 TTY 并启用 FPU。
2. 建立 GDT/TSS 和 IDT，屏蔽传统 PIC。
3. 初始化 PMM、内核页表根、堆和模块分配器。
4. 映射 LAPIC 与 PCI 配置空间，初始化 LAPIC、I/O APIC 和 syscall MSR。
5. 运行同步 VMA、CPIO、LaFS、块设备和 x86 用户加载器检查；在 PCI 枚举及真实 virtio-blk 初始化前清理模拟设备、CPIO 归档与 LaFS 挂载状态。
6. 发现 e1000 中断线；建立 BSP 正式上下文、idle 和主线程，随后发布 AP 入口。
7. 选择基础、测试或显式兼容模式并参与上线屏障；测试模式保留两份上下文，仅测试和兼容模式启动运行期自测试。
8. 释放配置任务，启用中断并进入监视器与主线程调度循环。

上述顺序表达初始化依赖，不保证每阶段均有事务式失败恢复。例如，缺少必需响应导致 panic；缺少 virtio 块设备则输出跳过消息。

该顺序可以划分为三个门槛：

```text
接受引导程序契约 -> 建立内核内存/CPU 状态
                  -> 初始化设备和任务
                  -> 启用中断并释放调度
```

在 IDT、控制器和每 CPU 状态准备好之前启用中断，可能将普通异步事件变成早期启动故障。在分配器、页表根或调度器状态准备好之前启动任务，也会产生类似的所有权问题。

## 共享阶段完成契约

`kernel/boot_phase.h` 为 x86_64 与 ARM64 分支定义相同的逻辑边界。BSP 在本地 IRQ 屏蔽状态下依次完成：

```text
memory -> bootstrap-tests -> devices -> runtime -> smp -> services
```

| 边界 | 完成条件 |
| --- | --- |
| `memory` | CPU 上下文、内存分配、平台异常与中断控制器状态可用 |
| `bootstrap-tests` | VMA/CPIO/LaFS/块设备 fixture 通过，临时共享状态已清理 |
| `devices` | 设备注册与探测完成，或按该启动路径明确跳过 |
| `runtime` | boot/idle 上下文、运行队列和任务配置已准备好 |
| `smp` | 所有预期 AP 通过架构屏障报告本地状态就绪 |
| `services` | BSP 配置任务释放与自测试启动已完成 |

`boot_phase_complete()` 拒绝跳过阶段、重复完成或在 IRQ 已启用时完成阶段。它先输出 `[boot] <phase> complete`，再以 release 顺序发布状态。已上线 AP 通过 acquire 读取等待 `services`，随后释放配置任务。架构上线屏障必须先结束，避免 BSP 等待依赖自身服务发布的 AP 工作。AP 超时不能视作 SMP 完成。

有状态单元测试只在 `memory` 与 `bootstrap-tests` 之间运行，早于 PCI/真实块设备注册和真实 initrd 加载。清理范围包括模拟块设备注册表、CPIO 归档与游标、LaFS 挂载元数据。运行期的 `@test vma`、`@test cpio`、`@test lafs` 和 `@test block_device` 仅报告缓存结果，不替换真实文件系统或注销设备。早期测试失败会停止启动。详细约束与宿主日志检查器见 [测试架构](../testing/testing-arch.md#startup-dependencies-and-completion-conditions)。

ARM64 直启在平台初始化前 park AP；Limine 路径保留固件映射并单独完成 AP GIC 设置。这些机器相关步骤仍然不同。Limine 明确跳过 PCI 时可以完成 `devices`，但不构成存储验证。统一逻辑完成点不要求各架构调用完全相同的硬件初始化函数。

## AP 初始化顺序

`start_smp()` 将 `secondary_cpu_init` 写入各辅助 CPU 的 Limine `goto_address`。AP 建立 GS，采用内核页表根，加载 GDT/TSS 和 IDT，初始化 LAPIC 及每 CPU 状态，配置 syscall MSR，随后参与 `wait_online()`，等待 `services` 完成后释放任务、启用中断并调度。

即使 IDT 表等对象共享，每 CPU 仍须加载对应描述符寄存器。MSR 配置同样只影响执行该操作的 CPU，BSP 启动成功不能证明 AP 已准备完毕。

AP 上线是本地契约：被 `wait_online()` 计数之前，AP 必须具备有效 GS、描述符表、中断控制器状态、页表根和调度器状态。共享 IDT 等对象不能免除每 CPU 寄存器和 MSR 设置。

BSP 在发布 AP 入口前建立主线程及 idle；AP 使用独立启动 TCB。
`cpu_assert_sched_context_ready()` 检查本地上下文、线程归属、状态和栈等条件，
两个入口均在 `sti` 前调用。主线程保持 RUNNING，并按当前调度器约定驻留运行队列，
以便切出后再次被选中；上下文检查不能代替架构寄存器与控制器初始化。

## 启动文件集合与配置上下文

x86_64 默认从独立 initrd 加载基础配置；`boot=test` 增加独立测试上下文，
`boot=compat` 显式启用旧 Limine 配置。来源之间不回退，救援用途尚无独立启动
模式入口。实施记录见 [启动载荷计划](../../process/boot-payload-refactor-plan.md)。

`boot_files.h` 提供借用的文件视图和独立文件集合，适配来源可以是通用启动
模块列表或 CPIO 归档。查找规范化斜线和 `.`，拒绝 `..`、跨来源限定名和过长
路径，按完整路径精确匹配。组件短名称在 `/task/` 下查找，配置使用明确路径。
缺失、无效和重名歧义分别返回；集合之间不隐式回退。CPIO 目录被跳过，符号
链接和特殊文件暂不支持。

`task_conf_init_ctx()` 将零初始化的上下文绑定到文件集合和用途：基础、测试、
救援或兼容。任务、测试指令、缺失模块策略、配置路径和逐 CPU 提交状态均由
该上下文持有。基础/救援上下文拒绝 `@test`，测试/兼容上下文可以记录。解析
失败清理部分记录并复位策略；成功解析后不能重复解析，开始执行后不能销毁
或重新初始化。任务提交在 `task_lock` 下领取 CPU 执行权，避免重复提交。

显式接口为 `task_init_ctx()` 和 `task_run_configured_cpu_ctx()`。x86_64 入口
和统计显示共用默认上下文，按基础或兼容用途显式初始化。测试模式另建绑定
Limine 测试集合的 `test_conf`；尚未迁移的架构路径
仍保留旧适配接口。selftest 的载荷查找使用选中上下文的文件
集合，但执行引擎仍只允许一个会话，第二次启动返回失败；独立解析不等于测试
可以并发执行。

`cpio_reader` 为各归档提供独立游标；旧 API 通过默认 reader 保留早期测试接口。打包器和解析器已修正为 newc 的“头部＋文件名”四字节对齐，
旧归档应重新生成，不再支持原先只对文件名填充的非标准布局。解析器检查范围、
十六进制字段、名称和截断。描述符、路径及载荷仍为借用存储，不能提前回收。
本阶段不实现引导器内存回收或 VFS。

`make test-boot-context` 在宿主上以 ASan/UBSan 编译真实适配层和解析器，检查
来源/游标隔离、精确匹配、歧义、损坏归档、用途限制、分配失败清理和执行权。
真实任务执行仍由 QEMU 门禁分别验证。

## 配置用户程序的构造路径

基础、测试与兼容配置的 type-3 任务统一通过 `create_elf_process()` 创建独立用户页表，
由任务层命名并入队。x86_64 原有手工嵌入式 ELF 加载器及未入队的线程已移除。
来源选择改变文件集合，不改变用户加载路径，所有权与入口规则见
[用户态架构](../user/user-arch-zh.md)。

设备注册前，`test_user_loader_run()` 构造并销毁不入队的合成用户进程。预热堆
扩展后，重复四轮成功加载和非法栈参数失败，检查 CR3、空闲物理页数与活跃堆
字节恢复。失败发生在段映射之后，可验证部分地址空间清理；不覆盖所有分配
失败注入，也不证明运行期退出后的僵尸线程最终回收。

## 验证与限制

```sh
make test-x86_64
make test-x86_64-smp-tlb
```

普通目标检查运行标志及命名自测试结果，TLB 目标提供专项跨 CPU 转换依据。两者都不能证明通用固件兼容性或任意 CPU 拓扑支持。其他验证应按 [测试矩阵](../testing/testing-arch.md#coverage-matrix)选择。

启动证据应按阶段记录：接受启动响应、内存所有权、BSP 架构设置、AP 上线完成、设备发现、任务构造以及最终进入中断/调度。最终运行标志只能证明选定路径到达监视器，不能证明所有可选设备或用户任务均已成功完成。

## 独立基础 initrd 打包

`make initrd` 从 `conf/task-base.conf`、`user.elf`、`module_foo.mo` 和
`e1000.mo` 生成 `build/initrd-x86_64.cpio` 及 JSON 清单。组件列表显式列出，
不收集测试载荷。默认配置只在 CPU0 启动用户程序与 worker；e1000 作为可用
组件打包，但没有自动启动条目。`INITRD_TASK_CONF` 可指定其他基础配置。

打包器规范化路径、拒绝重名并检查 ELF64 的架构和类型头。发布前，宿主检查器
通过真实 CPIO、文件集合和配置解析实现，以 `TASK_CONF_BASE` 加载
`/conf/task.conf`。测试指令、语法错误、路径歧义和缺失引用均导致失败，即便
配置声明跳过缺失模块也不例外。这些检查证明打包及引用完整性，不证明重定位
或运行期服务就绪。

条目顺序、所有者和 inode 编号固定；修改时间默认为零，可由
`SOURCE_DATE_EPOCH` 指定。清单记录文件大小、哈希、ELF 类型与架构，以及
归档哈希。验证失败保留已有产物。`make test-initrd` 验证确定性、逐字节内容
和错误输入拒绝。

## 外置 initrd 启动

`make iso-base` 生成 `build/base/LaOS.iso`，Limine 以 `/boot/initrd.cpio` 交付
整个归档。配置与载荷借用这段内存，当前不回收引导器内存。
`boot=base`（命令行缺失或为空时也按此处理）只接受归档内的
`/conf/task.conf` 和组件。归档缺失、歧义、CPIO 损坏、基础配置无效、组件引用
缺失或目标 CPU 不可用均停止启动。基础模式仅接受驱动、内核线程和用户任务，
拒绝测试指令。组件存在但加载失败时记录错误并跳过，后续任务继续执行。

`boot=compat` 显式启用原有 Limine 配置及模块集合；未知命令行被拒绝。
`make`、`make iso` 和 `make run` 已默认使用基础模式；兼容模式需显式设置
`X86_64_BOOT_MODE=compat`。原 `conf/task.conf` 保留给兼容及 ARM64 旧路径。
各模式均不跨来源补齐文件。x86_64 不再依赖嵌入头文件；
`embedded-initrd` 仅保留给仍需它的架构迁移路径。

`make test-x86_64-initrd` 检查基础来源、实际入队、worker 进展、用户系统调用
退出、三个并存用户根的独立性、截断 ELF 拒绝后其他任务继续执行，以及缺失、
损坏归档、配置和测试指令等失败场景。缺失引用场景额外交付同名 Limine 独立
组件，仍须失败，证明没有来源回退。日志位于 `build/base/`；各场景的串口、
QEMU 和构建日志在 `cases/` 下。这是 x86_64 QEMU TCG 证据，不覆盖 ARM64 或
其他引导器。

## 显式测试模式

`make iso-test` 生成 `boot=test`、基础归档及独立 `/conf/test.conf`。
`X86_64_TEST_CONF` 默认为 `conf/test.conf`，专项配置采用
`conf/test-x86_64-*.conf` 命名。语法与 task.conf 相同，用途和文件集合决定
语义。测试模式要求基础归档和测试配置均有效，不会在两份配置中选一份替代。

全局基础上下文保留自己的任务与策略；另一个测试上下文持有测试指令、fixture
任务和逐 CPU 提交状态。测试集合排除运输归档。SMP 完成后，仅测试上下文交给
单会话 selftest 引擎；每个 CPU 分别提交一次基础任务与测试任务，始终在各自
集合中查找。任务入队不代表服务就绪；有设备或服务依赖的测试仍需建立条件。

测试模式单独交付的用户及 worker 镜像作为回归 fixture，同名副本也独立于
基础组件。普通镜像只包含内核、归档和引导器文件；重建时清理 ISO 暂存树，
防止从测试切回基础模式时遗留测试文件。既有 x86_64 门禁显式选择测试模式。
多用户门禁要求三个 fixture 的退出及基础用户完成，额外基础任务不能掩盖
缺失的测试结果。

`make test-x86_64-boot-modes` 使用内容带不同标记的同名 ELF，验证分别执行、
基础模式忽略附带测试配置、测试配置缺失停止启动、测试组件不回退到 initrd，
以及测试模式必须提供基础归档。还会先构建测试模式、再按默认方式构建基础
模式，并检查真实 ISO 文件清单。不提供并行 selftest 会话、配置热重载或所有
内置测试的 `.mo` 迁移。

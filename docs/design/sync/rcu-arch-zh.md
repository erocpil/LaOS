# RCU 架构

英文原文：[RCU architecture](rcu-arch.md)。

## 适用范围

LaOS 在共享内核代码中实现了小型可抢占 RCU 宽限期机制。受支持的使用条件包括线程上下文中的读者、稳定的在线 CPU 集合、写者同步等待，以及受控的教学和压力测试场景。

当前实现尚未构成通用 RCU 容器库。宽限期机制与容器发布规则需要分别审查；现有链表的前向发布和遍历已经采用 release/acquire 操作，其架构验证要求见后文。

## 状态归属

`kernel/rcu.c` 中的全局状态如下：

| 字段 | 用途 | 访问规则 |
| --- | --- | --- |
| `gp_seq` | 当前宽限期代次 | 使用原子操作 |
| `blocked_tasks` | 已被切出且仍处于读侧临界区的线程 | 持有 `blocked_lock` |
| `blocked_lock` | 保护跟踪链表 | 本地中断状态须满足调用路径约束 |

每 CPU 状态：

| 字段 | 用途 |
| --- | --- |
| `rcu_gp_seq_seen` | 在静止状态观察到的最新代次 |

每线程状态：

| 字段 | 用途 |
| --- | --- |
| `rcu_nesting` | 读侧临界区嵌套深度 |
| `rcu_blocked` | 线程是否位于全局跟踪链表 |
| `rcu_blocked_node` | 嵌入线程控制块的跟踪链表节点 |

`rcu_metric` 向统计监视器提供代次、等待计数和最近一次宽限期的周期数。这些指标用于观测，不参与同步决策。

## 读者状态机

```text
nesting=0
   |
   | rcu_read_lock
   v
nesting=1..N
   |
   | nesting > 0 时发生上下文切换
   v
blocked=true，节点已链接
   |
   | 再次获得调度并执行最外层解锁
   v
节点移除，blocked=false，nesting=0，
更新 CPU 已观察代次
```

只有正在执行某线程的 CPU 修改该线程的嵌套计数。调度器在更改 `current` 之前检查即将切出的线程。

当前代码依赖调用者正确使用接口，尚未拒绝解锁计数下溢、被跟踪线程的销毁或不平衡的临界区操作。

## API 与执行上下文契约

公开接口有意保持较小。下表描述当前实现，不是未来兼容 Linux 的接口规格。

| 操作 | 允许的上下文 | 调度行为 | 本地中断规则 | 锁规则 |
| --- | --- | --- | --- | --- |
| `rcu_read_lock()` | 仅线程上下文 | 接口本身不调度 | 不禁用中断 | 不获取 RCU 锁 |
| `rcu_read_unlock()` | 执行进入操作的同一线程 | 接口本身不调度 | 仅在移除被跟踪线程时禁用中断 | 不得在线程销毁后或未配对进入时调用 |
| `synchronize_rcu()` | 可调度线程上下文 | 等待时调用 `schedule()` | 遵循调用者和调度器路径 | 调用者不得持有活动读者所需的锁 |
| `rcu_note_context_switch()` | 调度器切换路径 | 在切换前调用 | 调用者已禁用本地中断 | 在该约束下获取 `blocked_lock` |
| `rcu_check_quiescent_state()` | 定时器 tick 路径 | 不调度 | 在中断处理完成前运行 | 不获取 `blocked_lock` |

通过 `rcu_nesting` 支持嵌套读侧临界区，但只有最外层解锁可以移除被跟踪记录或发布 CPU 静止状态。当前没有 IRQ 或 NMI 读侧变体。

## 调度器与定时器钩子

`kernel/timer.c` 在每次定时器 tick、中断处理完成之前调用 `rcu_check_quiescent_state()`。该函数仅更新当前 CPU 的序号；线程子系统尚未建立当前任务时提前返回。

`kernel/sched.c` 在以下条件下调用 `rcu_note_context_switch(prev)`：

- 已确定将切出 `prev`；
- 本地中断已禁用；
- 尚未替换 CPU 当前线程指针；
- 尚未执行架构上下文切换。

如果 `prev` 不在读侧临界区中，切换记录一个静止状态；否则，钩子将其加入 `blocked_tasks`，且不会重复插入。

钩子中的原始自旋锁依赖调度器入口已关闭本地中断的约束。`rcu_read_unlock()` 获取同一锁之前禁用本地中断，以保持一致的本地中断保护规则。

## 宽限期算法

`synchronize_rcu()` 原子递增 `gp_seq`，并保存返回的目标代次。

第一阶段遍历当前 `g_cpu_contexts` 条目，等待各参与 CPU 满足 `rcu_gp_seq_seen >= target`。定时器 tick、非读者上下文切换或读者最外层解锁均可推进该值。

第二阶段在锁保护下反复检查 `blocked_tasks`，并通过调度等待链表为空。

两个阶段完成后，目标代次之前开始的读侧临界区已经在运行时退出、由 CPU 静止状态确认结束，或已作为被切出读者记录并随后解锁。

上述两类观察必须结合使用，单独任一类都不能构成安全保证：

1. 只有当前线程不在读侧临界区时，才能更新 CPU 已观察代次；
2. 读者在嵌套状态下被切出后，在最外层解锁并从 `blocked_tasks` 移除之前，都不能视为静止；
3. `synchronize_rcu()` 只有在所有参与的 CPU 跨过目标代次且跟踪链表为空后才返回。

当前实现不会为每个读者保存代次快照，而是通过调度器切换钩子，将被抢占的读者从 CPU 局部进展跟踪转移到全局跟踪链表。因此，调度器钩子、跟踪链表锁和最外层解锁共同构成宽限期的正确性边界。

算法依赖以下前提：

- 整个等待期间，`g_cpu_count` 及上下文指针保持稳定。
- 每个计入等待的 CPU 持续处理 tick 或执行调度。
- 调用者允许调度。
- 调用者不持有读者完成访问所需的锁。
- 序号比较不跨越整数回绕边界。
- 并发写者不依赖未定义的执行顺序。

实现没有超时机制。进展条件被破坏时，等待可能无限持续。

当前控制流等价于：

```text
target = 原子递增(gp_seq)

遍历稳定的每个 CPU 上下文：
    当 cpu.rcu_gp_seq_seen < target 时：
        schedule()

重复：
    获取 blocked_lock
    done = blocked_tasks 为空
    释放 blocked_lock
    若 done：
        返回
    schedule()
```

代次比较使用普通单调整数比较，仅在序号未回绕时有效。该等待是保守的：目标代次之后开始的读者，如果被观察为当前读者或随后进入 `blocked_tasks`，仍可能延迟返回。这不会削弱安全性，但意味着当前实现没有加速或按读者代次筛选的宽限期。

### 典型竞态边界

关键交错情况如下：

1. **代次递增之前进入的读者。** 仍在运行的读者会阻止其 CPU 在解锁或被切出之前发布目标代次；若在嵌套状态下被切出，调度器会将其记录到 `blocked_tasks`。
2. **第一阶段观察 CPU 之前读者已被抢占。** CPU 随后运行其他任务并报告进展，但被抢占读者仍独立存在于 `blocked_tasks` 中；第二阶段会阻止过早回收。
3. **代次递增之后进入的读者。** 它不属于本次宽限期的必要等待对象，但当前全局链表没有记录代次。如果它在写者检查链表前被切出，写者也可能等待它。
4. **最外层解锁与写者检查并发。** 解锁在 `blocked_lock` 保护下移除节点，写者也在同一把锁下检查链表，因此只能看到仍链接的读者或已经完成的移除，不会看到部分修改的链表。

这些边界说明了实现为什么依赖调度器钩子和锁顺序，而不只是依赖围绕 `gp_seq` 的原子操作。

## 发布与回收

宽限期机制用于确定旧读者何时完成。容器代码还须单独提供写者互斥、对象初始化与发布、读者 acquire 语义、保留遍历状态的移除操作，以及宽限期之后的回收。

`kernel/list.h` 中的 RCU 辅助接口保留被移除节点的链接，并使用 release-store/acquire-load 发布和遍历前向链接。

链表接口有意保持较窄的契约：

- RCU 只保证沿 `next` 的前向遍历；
- `prev` 仅供写者维护，不构成反向遍历保证；
- 写者仍须在 RCU 之外独立串行化链表更新；
- `list_first_entry_rcu()` 要求链表非空，当前尚未提供返回空指针的辅助接口；
- 读者不得在最外层解锁后继续保存或使用节点指针。

| 项目 | x86_64 | ARM64 |
| --- | --- | --- |
| 宽限期代次原子操作 | 编译器原子原语 | 编译器原子原语 |
| 调度器与定时器钩子 | 已接入 | 通过共享代码接入并编译 |
| 链表发布顺序 | release/acquire，通常生成普通 `mov` | release/acquire，生成 `STLR`/`LDAR` |
| 有界链表验证 | `rcu_publish` 自测试 | 自测试及指令形式检查 |

链表接口约束已不依赖特定架构。架构相关的验证应由构建检查承担，而非依赖调用者对硬件顺序的假设。

## 异步回调架构方案

本节定义后续设计约束，不描述已实现的功能。LaOS 当前仅提供同步宽限期等待，尚无 `struct rcu_head`、回调队列、工作线程或 `rcu_barrier()`。

### API 与所有权

拟议的公开记录为内嵌队列节点：

```c
struct rcu_head {
	struct rcu_head *next;
	void (*func)(struct rcu_head *head);
};

void call_rcu(struct rcu_head *head,
	      void (*func)(struct rcu_head *head));
void rcu_barrier(void);
```

调用者在待回收对象中内嵌 `rcu_head`，先从所有 RCU 发布结构中移除对象，再调用 `call_rcu()`。提交成功后，记录及所属对象的临时所有权交给 RCU，直至回调完成。同一记录重复提交属于非法操作，调试构建应予以检测。

`call_rcu()` 保证 `func(head)` 仅在可能早于提交的相关读侧临界区全部完成之后执行，但不保证回调执行时不存在新读者。

### 队列状态与批次边界

初始实现应采用明确的状态模型，无须直接引入 Linux 式可扩展的每 CPU 回调层次结构：

| 状态 | 含义 |
| --- | --- |
| `pending` | 已提交，但尚未归入已启动宽限期的回调 |
| 工作线程局部 `batch` | 启动对应宽限期之前已经封闭的回调批次 |
| `executing` | 宽限期已完成，当前回调接管记录 |

回调队列应使用独立锁，不应复用 `blocked_lock`。后者保护被切出读者的状态，并在调度器及最外层解锁路径中获取。将回调提交合并到该锁会引入不必要的顺序和中断上下文依赖。

工作线程必须先分离一个固定批次，再启动其宽限期：

```text
提交 A、B、C
        |
工作线程：分离 pending -> 局部 batch
        |
工作线程：synchronize_rcu()
        |                       提交 D -> 留在 pending，等待下一批次
        v
执行 A、B、C
        |
下一宽限期可以覆盖 D
```

宽限期进行期间提交的回调，不能直接追加到该宽限期结束后执行的批次。相应对象可能在宽限期开始之后才移除，读者也可能在宽限期开始之后取得该对象。最简单的安全规则是将新提交保留在 `pending`，交由下一宽限期覆盖。后续采用代次标记合并批次时，必须证明同等覆盖关系。

### 提交与工作线程路径

提交路径示意如下：

```c
void call_rcu(struct rcu_head *head, rcu_callback_t func)
{
	head->func = func;

	spin_lock(&callback_lock);
	append_fifo(&pending, head);
	wake_rcu_worker();
	spin_unlock(&callback_lock);
}
```

工作线程示意如下：

```c
for (;;) {
	wait_for_callbacks_or_shutdown();

	spin_lock(&callback_lock);
	batch = detach_pending();
	spin_unlock(&callback_lock);

	if (!batch.empty)
		synchronize_rcu();

	while ((head = pop_front(&batch)) != NULL)
		head->func(head);
}
```

以上为设计伪代码。实际实现必须使队列发布及唤醒与工作线程的休眠判断相互协调，避免唤醒丢失导致回调滞留。不得持有 `callback_lock` 调用 `synchronize_rcu()` 或执行回调，因为这些操作可能调度、获取其他锁、提交新回调，或执行较长时间。

教学实现使用单个全局 FIFO 即可，并能明确同队列回调顺序。每 CPU 队列应在顺序、排空和热插拔约束经过测试之后再考虑。

### 执行上下文约束

初始工作线程应采用普通可调度内核线程，因为现有 `synchronize_rcu()` 调用 `schedule()`。回调执行规则仍须明确选择：

- Linux 兼容回调可能在禁用下半部的上下文中执行，不能阻塞。
- LaOS 专用的纯工作线程约束可以允许阻塞，但调用者不能据此假定 Linux 回调语义。

初始方案宜规定回调短小且不阻塞。需要休眠的回调应另行提交线程上下文工作。执行回调时不得持有 RCU 内部锁。

提交上下文属于另一项约束。若允许从中断上下文调用 `call_rcu()`，队列锁及唤醒操作必须具备 IRQ 安全性。首先支持线程上下文提交，与当前不提供中断/NMI 读侧变体的 RCU 范围一致。

### 屏障、关闭与背压

`rcu_barrier()` 等待屏障记录之前提交的回调完成，而非仅等待一个宽限期。简单 FIFO 实现可以入队一个完成回调，再等待该回调执行。关闭顺序应为：

1. 停止生产者或拒绝新提交。
2. 执行 `rcu_barrier()`。
3. 停止回调工作线程。
4. 销毁回调依赖的代码与状态。

仅调用 `synchronize_rcu()` 不足以完成关闭，因为宽限期结束不能证明已经具备执行条件的回调实际执行完毕。

读者停滞时，异步更新可能持续积累未回收内存。应提供待处理、等待中和已执行回调计数、最旧回调等待时间、宽限期持续时间，以及现有滞后 CPU 和被跟踪线程状态。还需制定有界测试策略或写者背压机制，避免回调队列掩盖宽限期停滞，直至内存耗尽。

### 验证要求

回调实现需要覆盖以下测试：

- 移除、提交、旧读者退出、回调和最终释放的顺序。
- 宽限期内提交的回调延后至下一个安全批次。
- 同队列回调 FIFO 顺序。
- 回调内部再次提交回调。
- 并发提交与工作线程唤醒不丢失工作。
- `rcu_barrier()` 等待回调，而非仅等待宽限期。
- 空队列及回调处于各状态时的关闭。
- 调试构建拒绝重复提交。
- 回调积压和读者停滞诊断。
- x86_64 和 ARM64 运行验证。

## 禁用配置的语义

`CONFIG_RCU=0` 时，`kernel/rcu.h` 为接口提供内联无操作版本，且不注册 `rcu_stress` 自测试。

该配置保持编译兼容并消除热路径开销，但不会模拟宽限期。并发可见对象的移除与释放只有在另一种生命周期机制替代 RCU 时，才能在禁用 RCU 后保持正确。

## 测试结构

`kernel/test_rcu_publish.c` 提供较短的常规启动测试；`kernel/test_rcu_stress.c` 提供可配置专项负载。

两个测试的回收覆盖范围不同。`rcu_publish` 在 `synchronize_rcu()` 后复用一个静态节点，因此验证发布、观察、摘链和宽限期顺序，但不调用 `kfree()`。`rcu_stress` 每轮分配并释放节点，并主动切出启动阶段的每个读者，因此覆盖被抢占读者路径和实际回收顺序。

### 可配置压力测试

- `readers` 指定读者线程数，上限为在线 CPU 数。
- 一个写者运行在 CPU 0。
- 各读者在启动读侧临界区中主动执行一次上下文切换。
- 先执行包含被切出读者的初始宽限期，随后每轮执行一次回收宽限期。
- 每轮移除之前执行发布与观察握手。
- 检查超时、完成轮数、访问次数、跟踪路径及空链表状态。

标准结果标志如下，日志文本保持原样：

```text
[rcu_stress] PASSED: completed=N/N visits=... blocked_hits=... list_empty=1
[selftest] 'rcu_stress' PASSED
```

该测试覆盖前向遍历和单写者，不覆盖反向遍历、并发写者或代次回绕。较短的 `rcu_publish` 标志仍由普通 x86_64 和 ARM64 Limine 测试要求。

当前没有 `test-arm64-limine-rcu-stress` 目标。ARM64 具备常规 `rcu_publish` 运行检查及 `LDAR`/`STLR` 目标代码检查；包含被抢占读者、分配和释放的专项压力负载目前通过 `make test-x86_64-rcu-stress` 执行。

验证证据与设计覆盖的对应关系如下：

| 证据 | 覆盖内容 | 不证明的内容 |
| --- | --- | --- |
| `rcu_publish` | 前向发布、acquire 观察、摘链、同步复用 | 堆释放、被抢占读者压力、多个写者 |
| `rcu_stress` | 主动抢占读者、跟踪链表、宽限期后的分配与释放 | 反向遍历、并发写者、代次回绕 |
| `check_arm64_rcu_order.sh` | ARM64 生成的 acquire/release 指令形式 | 运行时进展或所有编译器/硬件行为 |
| x86_64/ARM64 普通测试 | 与启动、调度器和测试框架的集成 | 通用 RCU API 兼容性 |

## 失效情形

| 情形 | 可观察影响 |
| --- | --- |
| 读者始终不解锁 | 跟踪链表无法清空，或 CPU 观察代次无法推进 |
| 计入等待的 CPU 停止处理 tick 或调度 | 第一阶段永久等待 |
| 调用者持有读者需要的锁 | 宽限期死锁 |
| 线程仍位于跟踪链表时退出 | 残留节点及释放后使用风险 |
| 节点过早释放 | 读者访问已释放对象 |
| release/acquire 语义退化 | ARM64 指令检查失败，或读者观察到不一致字段 |
| 序号回绕处理不当 | 代次顺序产生歧义 |

`CONFIG_RCU_DEBUG` 有助于检查节点链接和移除过程，但当前没有用于识别具体停滞原因的检测器。

## 后续演进顺序

1. 增加不变量检查与宽限期停滞报告。
2. 在其他子系统确有需要时，将 release/acquire 原语扩展到 RCU 链接之外。
3. 持续保留 ARM64 指令检查及运行测试。
4. 明确定义并串行化并发写者行为。
5. 增加回调记录与 `call_rcu()` 工作线程。
6. 在正确性测试建立后，再合并回调批次和宽限期。

在进展条件与内存顺序约束尚未明确时引入异步回调，只会将阻塞从调用者路径转移到后台，不能消除原有失效原因。

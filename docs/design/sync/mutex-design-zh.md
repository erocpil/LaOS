# 互斥锁架构

英文原文：[Mutex architecture](mutex-design.md)。

获取锁及优先级捐赠示例见 [互斥锁教程](mutex-tutor-zh.md)。[第 7 章](../../book/07-synchronization-zh.md)比较互斥锁、自旋锁与 RCU 的适用条件。

## 适用范围与状态

LaOS 提供统一的互斥锁 API，并通过编译配置选择两种策略：

- `CONFIG_MUTEX_HANDOFF=0`：raw 策略，解锁后唤醒等待者，允许新到达线程抢先获取锁（barging）。
- `CONFIG_MUTEX_HANDOFF=1`：handoff 策略，将所有权直接移交给选定的等待者。

两种策略均采用按优先级排序的等待队列和单跳优先级继承。`struct mutex` 包含 `locked`、`owner`、`donated_priority` 及受锁保护的等待队列。

`waiters.lock` 保护等待者链表及计数、互斥锁路径上的所有者转换，以及该锁关联的优先级捐赠。等待者按有效优先级排列，数值越小，优先级越高。相同优先级的新等待者插入已有等待者之后，以保持 FIFO 顺序。

阻塞线程仍保留在所属 CPU 的运行队列中。`__wake_up_one()` 仅移除 `wait_node` 并将选定任务置为 READY，不得再次插入同一个运行队列节点。

## API 与执行上下文契约

`mutex_lock()` 是可能睡眠的操作，只能在线程可以阻塞且所有者能够继续运行的上下文中调用。不得在 IRQ 处理程序中调用，不得持有所有者完成进展所需的自旋锁，也不能把禁用本地中断当作跨 CPU 互斥机制。

| 操作/路径 | 是否可能调度 | 本地中断规则 | 主要保护 |
| --- | --- | --- | --- |
| `mutex_lock()` 快速路径 | 否 | 保留调用者中断状态 | 原子锁及所有者更新 |
| `mutex_lock()` 竞争路径 | 是 | 使用保存中断状态的方式获取等待队列锁 | `waiters.lock` 与队列成员关系 |
| `mutex_unlock()` | 否 | 使用保存中断状态的方式获取等待队列锁 | 所有者、捐赠和等待者转换 |
| `mutex_lock_handoff()` 确认 | 否 | 保留调用者中断状态 | acquire 语义观察 `owner` |
| PI 刷新 | 否 | 遵循互斥锁路径的锁顺序 | 所有者 PI 计数和运行队列迁移 |

当前实现要求所有者释放自己持有的互斥锁，不提供递归锁、锁顺序校验、死锁检测或 IRQ-safe 互斥锁。阻塞等待者仍由调度器管理；从互斥锁等待队列移除它，与从运行队列移除其节点是两个独立操作。

## 状态转换

竞争获取路径的主要状态如下：

```text
空闲
  | 原子获取
  v
已持有(owner=current)
  | 其他线程获取失败
  v
等待者入队，current=BLOCKED，刷新捐赠
  | 所有者唤醒一个等待者
  +------------------------------+
  | raw                           | handoff
  v                               v
空闲 + 选中等待者 READY           已持有(owner=选中等待者)
```

raw 策略下，选中的等待者运行后仍须重新竞争；handoff 策略下，锁保持逻辑持有状态，选中等待者直接消费预留的所有权。两条路径都必须且只能移除一次选中等待者的 `wait_node`。

## 优先级捐赠模型

每个互斥锁向所有者捐赠其最高优先级等待者的有效优先级。该值发生变化时，先撤销旧捐赠，再添加新捐赠。所有者按优先级保存捐赠计数，以正确聚合多个已持有互斥锁的贡献：

```text
基础优先级=48，锁 A 捐赠 16，锁 B 捐赠 8 -> 有效优先级=8
释放 B -> 有效优先级=16
释放 A -> 有效优先级=48
```

关联所有者时，根据已有等待者计算捐赠；解除关联时，在清空所有者指针之前撤销该锁的捐赠。raw 和 handoff 路径共用这些辅助操作。

锁获取顺序如下：

```text
mutex.waiters.lock
    -> owner.pi_lock
        -> 所有者的 runqueue.lock
```

调度器不会按相反顺序获取这些锁。

所有者 PI 计数是不变量：对于每个优先级，计数等于当前所有者持有且贡献该优先级的互斥锁数量。撤销某个互斥锁的捐赠必须发生在清空其所有者指针之前；刷新后的捐赠必须在确定新所有者之后再关联。这样可以避免释放一个互斥锁时暂时丢失其他互斥锁贡献的捐赠。

## raw 策略

快速获取使用具有 acquire 语义的比较交换。慢路径获取 `waiters.lock` 后再次尝试获取锁，以关闭唤醒丢失窗口；随后将当前线程置为 BLOCKED，按优先级及同级 FIFO 顺序插入等待队列，更新捐赠，释放等待队列锁并调度。

解锁时，先获取 `waiters.lock`，解除所有者关联并撤销捐赠，在清除 `locked` 前发布临界区写入，最后唤醒最高优先级等待者。由于 `locked` 变为零时被唤醒任务不一定已经运行，新到达线程可能抢先获取锁。优先级继承用于抑制原所有者持锁期间的优先级反转；raw 策略不保证解锁后的获取公平性。

防止丢失唤醒的关键顺序如下：

```text
等待者：快速路径失败
等待者：获取 waiters.lock，再次尝试获取
等待者：标记 BLOCKED 并链接 wait_node
等待者：刷新捐赠，释放 waiters.lock，调度

所有者：获取 waiters.lock，解除关联/发布，唤醒选中等待者
所有者：释放 waiters.lock
```

如果所有者在第一次失败和第二次尝试之间释放，等待者会直接获取互斥锁而不会睡眠；如果释放发生在等待者入队之后，同一把 `waiters.lock` 会串行化唤醒和队列成员关系。

## handoff 策略

存在等待者时，解锁保持 `locked=1`，撤销旧所有者的捐赠，唤醒最高优先级等待者并将其关联为新所有者。被选中的任务以 acquire 语义观察到 `owner == current` 后，直接从 `mutex_lock_handoff()` 返回，无须竞争 `locked`。

该策略阻止新到达线程抢先获取锁。相同优先级按 FIFO 移交，不同优先级按等待队列顺序选择。没有等待者时，解除关联、发布写入和清除锁状态的过程等价于普通释放。

## 优先级反转

```text
low(48)：    获取 M ---------------- 执行 -------- 释放 M
high(8)：                获取 M -> BLOCKED        获取成功
medium(32)：                       READY

捐赠：high(8) -> M -> low
low 有效优先级：48 -> 8 -> 48
```

high 阻塞后，low 的运行队列节点从优先级桶 48 移至桶 8，因此可先于 medium 运行。解锁撤销捐赠，并将 low 移回原优先级桶。

## 实现边界

当前继承不具有传递性：

```text
high 等待由 low 持有的 M1
low 等待由 very-low 持有的 M2
```

high 提升 low 的有效优先级，但该变化不会作为更新后的捐赠继续传递给 M2 的所有者。实现也没有死锁环检测。准确的能力描述是“支持多个互斥锁捐赠聚合的单跳优先级继承”，而非完整优先级继承。

对 BLOCKED 等待者的基础优先级修改会被拒绝，因为当前尚不能将等待队列重排与所有者捐赠更新作为一个串行化操作完成。

## 配置与验证依据

默认启动采用 raw 互斥锁，并禁用早期的无限循环互斥锁压力线程：

```text
CONFIG_MUTEX_HANDOFF=0
CONFIG_MUTEX_STRESS=0
```

优先级反转测试及相关 SMP 压力目标如下：

```sh
make test-x86_64
make test-x86_64-sched-stress
make test-arm64-limine
make test-arm64-limine-sched-stress
```

ARM64 目标须在 `arm64` 分支运行。默认运行测试覆盖 raw 策略。handoff 已有实现，但托管 CI 尚未为其设置独立构建变体。

实现传递性优先级继承之前，需要建立等待依赖链模型、有界传播、环处理、多互斥锁获取顺序及嵌套锁测试。支持阻塞线程优先级修改之前，需要实现原子的等待队列重排与捐赠更新操作。
